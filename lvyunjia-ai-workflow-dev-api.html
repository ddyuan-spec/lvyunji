绿韵家 Coze 工作流 · 后端对接文档

文档版本 V1.0 · 覆盖「帮我买 / 帮我选 / 帮我省」三入口 · 面向 App 后端，确保用户在 APP 的数据正确传入工作流

一句话结论：App 后端调用工作流时，把「用户本轮输入文本」+「入口类型（裸字符串 buy/choose/save）」+「会话 ID」+「用户 ID」+「图片（可选）」传给工作流开始节点即可。其余（意图解析、知识库召回、上下文拼接）全部由工作流内部完成，不要自己拼历史、不要自己判断意图。

一、背景与范围

项说明
工作流定位绿韵家 App「数智中心」智能助手，覆盖三个入口：帮我买、帮我选、帮我省
入口分流键开始节点变量 custom_variables，取值 buy / choose / save（写死的裸字符串，由 App 按钮决定）
工作流模式chatflow（对话型，支持多轮上下文）
本文目的给后端一份可直接联调的入参规范 + 踩坑清单，避免"数据传不进去 / 走错分支"
⚠️ 变量名以平台实际为准：以下变量名基于联调实测（Coze 工作流开始节点）。若你们 Coze 开始节点的字段名不同（如大小写、下划线差异），一律以 Coze 工作流编辑页「开始节点 → 输入变量」里显示的字段名为准，本文用逻辑名描述映射关系。联调第一步：请后端在 Coze 打开该工作流，截图开始节点的变量列表，与本文表逐一核对。

二、调用方式（二选一）

方案路径适用推荐度
方案一：Bot 对话 API App → Coze 对话消息 API（带 conversation_id）→ Bot 内部挂载的工作流 App 已有 Bot 会话通道，回复希望像真人对话一样流式回流 推荐
方案二：工作流直调 API App 后端 → POST /v1/workflow/run → 直接传开始节点参数 → 解析返回的节点输出 不需要 Bot 外壳，纯后端集成、自行渲染 UI 可选

无论哪种方案，入口类型 custom_variables 都必须随每次请求传入，否则工作流不知道走哪条分支。

三、入参 Schema（开始节点变量）

逻辑名Coze 变量名（参考）类型必填含义 / App 数据来源
用户本轮输入USER_INPUTString是用户在对话框输入的自然语言文本，如"我最近睡不着想买安神的"
入口类型custom_variablesString是由 App 端按钮决定：buy / choose / save。裸字符串，不要 JSON
会话 IDconversation_idString是（多轮）本次对话唯一标识，多轮问答必须复用同一 ID，否则上下文丢失
用户 IDuser_idString建议绿韵家 App 登录用户 ID，用于画像/个性化（当前工作流未强依赖，建议传）
图片列表user_imagesArray<String>否用户上传的图片 URL 数组（帮我选/帮我买带图识别时用）。无图传空数组 []
会话标题CONVERSATION_NAMEString否会话展示名称，可传"绿韵家数智助手"或用户首句
🚫 致命坑（已实测踩过）：custom_variables 的值必须是裸字符串 "buy"，不能传 {"analysis_type":"buy"} 这种 JSON 字符串。工作流选择器判断的是「开始.custom_variables == "buy"」，传 JSON 字符串会因整串不等而全走"否则"分支，三入口全部失效。

五、多轮会话与上下文

  • conversation_id 必须稳定复用：同一通会话的每一轮请求，传同一个 conversation_id。工作流 LLM 节点的"会话历史"开关会自动按此 ID 拉取历史（轮数 5~6 轮），App 端不要自己拼历史对话传进去。
  • 指代理解由工作流负责：如第一轮问"助眠的有什么"，第二轮问"那个贵不贵"，工作流内部结合会话历史能指向同一商品，App 只需传第二轮文本 + 同一 conversation_id。
  • 新会话：生成新的 conversation_id（建议 conv_{userId}_{时间戳} 或后端会话表主键）。

六、图片传入

字段格式要求
user_images图片 URL 字符串数组。URL 需为公网可访问（Coze 节点要能拉取）。无图传 []
大小限制遵循 Coze 图片节点限制（单张建议 < 10MB，具体以平台为准）
类型舌象/皮肤/面相/商品图均可，工作流按入口 + 节点路由到对应解读分支

七、返回值与渲染

调用方式最终回复在哪App 如何渲染
Bot 对话 API对话消息流中（工作流「输出节点」已将文案推到对话窗口）直接渲染消息流最后一条助手消息即可
工作流直调 API返回体里对应「输出节点」的 output 变量（如 帮我买输出.output）解析该字段，按 Markdown 渲染（回复含 ##### 标题 + emoji）
注意：Coze 工作流结束节点没有"返回内容"配置项，真正推给用户看的是「输出（消息）节点」。后端若走工作流直调 API，需读取输出节点的 output 变量，而不是结束节点。联调时确认工作流里有且仅有正确的输出节点连到结束节点。

八、后端必避的坑（来自联调实测）

#坑正确做法
1custom_variables 传 JSON 字符串 {"analysis_type":"buy"}传裸字符串 "buy"。选择器按整串相等判断，JSON 永远不匹配
2变量名大小写/下划线写错（如 CustomVariables、user_input）与 Coze 开始节点变量名逐字一致（区分大小写）
3走 Bot 但变量没映射，工作流收不到 custom_variablesBot 编排里配置「工作流输入 ← Bot 变量」映射；或改走工作流直调 API 直接传参
4多轮每次用新 conversation_id同一会话复用同一 ID，否则上下文丢失、指代失效
5自己拼 chatHistory 传进去不要传历史，工作流内部按 conversation_id 自动管理（轮数 5~6）
6问候/闲聊当成异常正常走"非产品分支"返回问候引导语，无需 App 特殊处理，只要 entry 传对
7意图识别放前端做意图解析（keywords / is_product）由工作流 parse_buy_query + 代码节点完成，前端只传入口类型 + 文本
