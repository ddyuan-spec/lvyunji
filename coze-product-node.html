三个实测发现的坑：
1. type=2 返回对象、0/1 返回数组 —— 代码里用 Array.isArray() 统一成数组，避免下游报错。
2. 后端返回顺序不能用 —— 同一 type 连续两次请求，结果集和顺序都在变（疑似按用户行为动态推荐）。所以「省」的差额降序、「选」的打分降序必须在代码节点里自己排，不能信后端顺序。
3. 只用 productMainImg —— productCoverImg 实测恒为 null。

#事项现状（实测）需要谁给

      

        ①
        商品图片完整 URL 前缀
        接口只返回相对路径 /common/2026/1/27/xxx.jpg；已试探 6 个候选域名均 404 / 无此域名，推测需要专门图片域名或 CDN
        后端
      

      

        ②
        生产环境 accessToken 来源
        文档给的是测试环境固定 token，硬编码会过期且泄露风险高
        后端（建议随 userId 由 App 网关透传，或提供 Coze 专用长期 token）
      

      

        ⑧
        「帮我买」(buy) 该走哪个 type
        本版按 buy → 2（按商品名查） 实现（我的推断）。但「帮我买」的用户句式是"我最近睡不着想买安神的"，属于需求推荐而非精确商品名，可能用 type=1 打分推荐更合适
        产品 + 后端定；定了改代码里 INTENT_TYPE 一行即可
      

      

        ③
        score 分数量纲
        实测出现 20 / 60 / 100 / 150 / 205 / 230，不是 0–100，标签「AI评分 230」不符合用户直觉
        产品定口径（归一化 100 / 换算十分制 / 不展示分数，只展示理由）
      

      

        ④
        推荐结果混入测试数据
        实测出现「专门测试bug ¥8.8」「彩色电视」「测试水卡模版 ¥9.9」，且 9.9 元商品差额为 0 却进「帮我选」Top1
        后端过滤测试商品 / 加白名单
      

      

        ⑤
        卡片副标题 desc 来源
        接口无描述字段，当前留空；原型卡片上有卖点文案
        产品定：留空 / 大模型生成 / 后端补字段
      

      

        ⑥
        推荐是否可复现
        同一 type 连续两次请求，商品集合和顺序都不同
        后端确认是随机还是按行为动态；如需可复现需加缓存/种子
      

      

        ⑦
        生产域名
        当前为 yxm-test-api.juhuanvip.com 测试环境；开始.env 已存在，可用来切环境
        后端（给正式域名后填进 ENV_HOSTS.prod，无需改逻辑）
      

      

        ⑨
        卡片 JSON 的传输通道
        本版设计为「输出节点用 ########## 拼接：前段文案 + 后段 card_json」，App 端解析渲染
        App 端确认是否接受此约定；若走 Coze 消息卡片则改用卡片变量映射
      

      

        ⑩
        悬空节点是否删除
        获取后端商品数据(153092)、获取后端商品卡片(147968) 是默认模板代码且无人引用
        你确认（建议删，避免误判"已接好"）
