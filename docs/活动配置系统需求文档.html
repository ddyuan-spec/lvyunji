📋 一、文档概述

1.1 背景与目标

绿韵家平台目前存在多种营销活动规则，包括限时促销升级、启航奖、鼓励奖等。这些规则目前以硬编码方式存在于系统中，每次调整都需要开发介入，响应周期长、灵活性差。

🎯 核心目标

构建一套运营自主配置活动系统，让运营人员可以在后台独立创建、编辑、上下线活动，设定有效期，自主调整活动规则，全程无需开发介入。

系统需要覆盖PDF《业绩相关紧急需求》中的三大核心场景：

  • 限时促销升级活动 — 有明确截止日期的等级晋升活动
  • 启航奖奖励政策 — 常态化的推荐奖励规则
  • 鼓励奖奖励政策 — 常态化的级别超越奖励规则

1.2 适用范围

维度说明
适用平台绿韵家后台管理系统（Web端）
使用角色运营人员、活动审核人员、管理员

3.2.5 活动模板库

支持将历史活动保存为模板，快速创建新活动：

  • 保存模板：任何状态的活动均可保存为模板，模板包含完整的规则矩阵和配置
  • 使用模板：从模板库选择模板，系统自动填充配置，运营只需修改日期和数值
  • 模板分类：按活动类型自动分类，支持搜索和筛选
  • 模板权限：支持设置模板可见范围（个人/部门/全公司）

3.3.2 冲突检测与处理

⚠️ 冲突场景示例

场景：同时存在"限时促销升级活动"和"日常升级规则"，会员当天自购PV达到6,300：

  • 限时活动：新人 → 直接晋升高级会员
  • 日常规则：新人 → 按累计PV逐步升级

处理策略：活动优先级高于日常规则。当活动生效期间，优先执行活动规则；活动未命中时，回退到日常规则。

冲突类型检测逻辑处理策略
活动 vs 日常规则同一触发条件同时命中活动和日常规则活动优先级高，优先执行活动规则
活动 vs 活动多个活动同时命中同一用户按优先级排序，高优先级先执行；互斥活动仅执行一个
规则矩阵内冲突同一当前等级+不同PV门槛映射到不同目标等级取最高目标等级（或配置时强制校验不允许）

3.3.3 防重复机制

防止同一会员重复享受同一活动：

  • 活动级去重：记录每个会员参与每个活动的次数，达到上限后不再触发
  • 规则级去重：同一活动内不同规则行独立计数
  • 幂等性保证：同一笔订单不会重复触发同一活动（通过订单ID+活动ID唯一索引）
  • 跨活动去重：支持配置"互斥活动组"，组内活动仅可参与一次

3.3.4 审计日志

所有活动触发都必须记录详细日志，便于对账和问题排查：

4.1 限时促销升级活动

4.3 鼓励奖奖励政策

4.3.1 业务规则还原

📋 原始需求摘要
  • 适用对象：成长达人、服务达人（以临时级别为准）
  • 停止等级：精英达人起不再发放
  • 奖励来源：每笔订单PV的1%
  • 分配规则：根据关系链从成长达人起，当会员级别被超越时发放
  • 同级平分：如果多人在同一区间内被超越，则同级平分1%
  • 级别阻断：更高级别会阻断奖励传递，仅靠近订单者可获得完整1%

4.3.2 系统配置方案

鼓励奖属于日常配置，在"日常配置 → 鼓励奖规则"中配置：

配置项配置值
规则名称鼓励奖
适用等级范围成长达人、服务达人
停止等级精英达人（达到后停止）
奖励比例订单PV的1%
分配方式同级平分
阻断规则更高级别阻断，靠近订单者优先
级别依据临时级别

4.3.3 计算示例

📊 示例：关系链 ④→④→③→②→④→③→②→③→②→⑤（推了1个900PV）

订单产生者等级为⑤，订单PV = 900

  • 三个④：在同一区间被超越 → 同级平分1% → 每人获得 900 × 1% ÷ 3 = 3 PV
  • 两个③：在同一区间被超越 → 同级平分1% → 每人获得 900 × 1% ÷ 2 = 4.5 PV
  • 靠近订单的②：与另一个②之间有更高级别③阻断 → 仅靠近订单的②获得完整1% → 9 PV
  • 另一个②：被③阻断 → 0 PV

🔒 七、非功能性需求

7.1 性能需求

指标要求说明
规则匹配响应≤ 100ms用户行为触发到规则匹配完成的耗时
活动列表加载≤ 500ms活动管理页面列表加载时间
并发处理≥ 1000 TPS高峰期订单触发规则引擎的并发处理能力
数据查询≤ 2s活动效果统计报表查询时间

7.2 安全需求

  • 权限控制：活动创建、编辑、审核、上线操作需不同角色权限
  • 操作审计：所有配置变更记录操作人、时间、变更内容
  • 数据校验：配置提交时进行完整性和逻辑校验（如结束时间必须晚于开始时间）
  • 防误操作：活动下线、删除等危险操作需二次确认

7.3 可靠性需求

  • 高可用：规则引擎服务可用性 ≥ 99.9%
  • 数据一致性：活动触发和奖励发放需保证事务一致性
  • 故障恢复：支持活动配置的版本回滚，故障时可快速恢复上一版本
  • 灰度发布：新活动支持按会员ID尾号灰度，验证无误后再全量上线

7.4 可扩展性需求

  • 活动类型扩展：支持通过插件方式新增活动类型，无需修改核心代码
  • 条件类型扩展：支持新增条件判断维度（如消费频次、商品品类等）
  • 动作类型扩展：支持新增执行动作（如发放优惠券、积分等）
